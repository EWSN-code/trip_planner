# 旅行比較機能: シニアアーキテクトによる設計レビュー

このレビューは前回プラン (`1787842567158-travel-comparison-investigation.md`) に対する批判的検証である。`app.js` `model.js` `storage.js` `cloud.js` `render.js` `editor.js` `route-wizard.js` `utils.js` `index.html` `styles.css` `theme.css` `data/initial-state.json` `config.example.js` を実コードで確認した上で、推測・過剰設計・保守性低下・スコープ膨張を列挙し、最後に最小実装案を提示する。

## A. 事実確認で問題が見つかった箇所

### A-1. `state.settings` の初期形に `theme` がない
- プラン §1, §2: 「`state.settings` の 2 階層」「`{selectedTripId, viewMode, theme}`」
- 実コード: `data/initial-state.json` は `{selectedTripId, viewMode}` のみ。`theme` は `model.js#normalize` のデフォルト引数で `|| "system"` として合成される
- 影響: 軽微だが「初期状態がクラウドから来た場合の形」と「コードが扱う形」の認識齟齬。実装側で `theme` を持つ前提の設計をしないこと

### A-2. `config.example.js` がプラン未記載
- 実在: リポジトリ直下に `config.example.js` あり (プレースホルダのみ)
- 影響: 軽微。`config.js` を取り違えた運用を防ぐため、プラン §1 のディレクトリ表に含めるべき

### A-3. プランの `config.js:1-7` 行番号は正しいが、`cloud.js` / `storage.js` の行番号は実コードと微妙にずれる
- プラン §3: `cloud.js:10` `fetchCloudState` / `cloud.js:11` `upsertCloudState` → 実コードは 11 行ファイルで fetch=10, upsert=11 で合致
- ただし `cloud.js:6-9` と書いたが `getCurrentSession` (6), `signIn` (7), `signUp` (8), `signOut` (9) の 4 行で実コードと一致
- 影響: 軽微。レビュー的には「行番号は目安、実コード参照」と注記すべき

## B. 設計上の問題点 (推測 / 過剰 / 保守性 / 最小変更 / 永続化 / スコープ)

### B-1. 「比較結果の保存/共有」が永続化前提で書かれている (UI 状態の永続化に該当する)
- プラン §5 比較モード表: 「比較結果の保存 / 共有 → `state.comparisons: [{id, name, tripIds, createdAt}]`」
- 批判: 比較は `state.trips` から純関数で導出できる派生的表示。選択中の ID 群は **UI のエフェメラル状態** であり、`localStorage` / Supabase に書く理由がない
- 結果: B-1 案は却下。比較対象は `URLSearchParams` またはセッション内変数のみ

### B-2. `version: 2` へのバンプ + マイグレーション提案が意味をなさない
- プラン §8: 「`version` を 2 にバンプ」「v1 → v2 のフォールバック」
- 批判: `model.js#normalize` にはバージョン番号を使う分岐が一切ない。バンプだけして読まずに `version: 1` を付け直すだけなら、バンプする意味がない
- 結果: 比較機能追加で `state` のトップレベル形が変わらないなら、バンプ不要。`state.trips` の `timeline[]` に項目を足す場合も、既存 `normalize` の `Array.isArray(s?.trips)` フォールバックで吸収できる

### B-3. 「最小実装」と称する (A) 案が実際は最小ではない
- プラン §7 選択肢 (A): 「費用・期間・項目数のサマリだけ」「`utils.js` + 一覧の拡張で完結。実装規模小」
- 批判: 「サマリだけ」を別画面で見せるには、最低でも以下が要る
  1. 一覧に「比較に追加」チェックボックス (HTML + CSS + JS)
  2. 比較対象を保持する UI 状態 (プランは `state.settings` を提案 → B-1 で却下済)
  3. 比較表示のセクション (`<section id="compareView">`) + ナビボタン + 表示関数
  4. `render.js` への追加 (`renderCompareSummary` 等)
  5. 検証
- 「`utils.js` + 一覧の拡張」だけでは完結しない。「実装規模小」は誤認。**`utils.js` の追加 + `index.html` + `app.js` + `styles.css` の 4 ファイル変更は確定**
- 結果: サイズ見積もりを訂正し、本当の最小を B-3 案として再提示する

### B-4. 推奨案 (B) の規模が著しく小さく見積もられている
- プラン §7 (B): 「`render.js` の追加と `styles.css` の 2 カラム」
- 批判: 既存の旅程詳細 (`#detailView`) は単一旅前提で、`#dayTabs` / `#timeline` / `top-summary` / `budget-grid` が直列に描画される。2 旅を並列にするには
  1. 比較専用の **新セクション** (現状の `#detailView` を複製する構造)
  2. ナビに比較タブ追加 (`#compareNav` の活性/非活性制御)
  3. 「比較する旅を選ぶ」UI (2 つ選択 → 確定) — プランはチェックボックスと書くが、比較セクション内 or 一覧かで曖昧
  4. 比較表示の関数 (タブ, 合計, 集計, タイムライン)
  5. 「片方が欠ける日」「時刻が前後している」「費用が高い」のような **比較ロジック** — プランは `compareTimeline` / `diffSummary` を出すが、これらは「2 つの配列を縦に並べるだけ」ではない。差分の意味を決める必要がある
- 結果: (B) を採用するなら、**比較ロジックの意味 (何を「差」と判定するか) を 1 つの例で確定してから実装に入る** ことが必要

### B-5. 比較の「起点」が未確定
- プラン §5: 「`#tripGrid` のカードに比較用チェックボックス」
- 批判: 一覧のカードにチェックボックスを置くと、「比較用に 2 つ選んで比較画面に行く」 UI と「カードをタップして詳細に入る」 UI が **同じカードを奪い合う**。特にスマホでは押し間違いが起きる
- 代替: 一覧の上部に「比較モード」トグルを置き、ON の時だけカードにチェックが出る形にすると、操作モードが排他になり UX が明確
- 結果: 一覧に常時チェックボックスを置く案を撤回

### B-6. プラン §6「技術的負債」に推測が混入
- 「共同編集や変更履歴には未対応」 → ユーザー要求にない。旅行比較機能のレビューには不要
- 「`__pycache__/` がコミット対象」 → 推測。`.gitignore` 未確認 (`.kilo/.gitignore` の存在は確認したが、リポジトリルートの `.gitignore` は未確認)
- 「ローテーション手順が README にない」 → 推測。`SETUP_SUPABASE.md` 全文未確認
- 結果: 技術的負債セクションからユーザー要求と無関係な項目を削除し、確認できた事項のみ残す

### B-7. 比較機能と関係のないリファクタ提案が紛れ込んでいる
- プラン §6: 「`$ = s => document.querySelector(s)` の重複」「`app.js` の肥大化」「`__pycache__/` の整理」
- 批判: これらは旅行比較機能の最小変更を逸脱するスコープ膨張。本プランの実装対象外にすべき
- 結果: 技術的負債は「旅行比較機能を素直に実装する上で**踏む必要のある**もの」だけ残す

### B-8. 検証計画が「画面で目視確認」止まり
- プラン §9: 「同一ブラウザで 2 旅を比較 → 印刷ビューでも同等の出力が得られるか目視確認」
- 批判: テストの自動化手段が一切ない (本リポジトリには `__tests__/` も `package.json` もない、ESM 純 JS)
- 結果: 目視確認は妥当だが、(a) どの旅を 2 つ用意するか (b) 期待する DOM 要素の存在 (c) 期待する集計値 (d) 印刷時の 1 ページ / 2 ページの判断基準、を **具体的なチェックリスト** にすること。`utils.js` の純関数 (`summarize`, `total`) だけは Node で実行可能なので、最低限の算術テストは導入可能

### B-9. 「触らなくてよいファイル」表が再考されていない
- プラン §5: `config.js` / `js/theme.js` / `js/cloud.js` は不要
- 批判: これは概ね正しいが、**`print/index.html` と `print/print.js` の扱い** をプランが書いていない。比較結果の印刷を今回スコープに含めるなら必要、含めないなら明示
- 結果: 印刷は **スコープ外** と明記する

### B-10. 推奨案 (B) に「ロールバック手順」があるが、`version` バンプを伴わない案では無意味
- プラン §8: 「ロールバックは `version` を 1 に戻すだけで対応可能」
- 批判: B-2 で `version` バンプは不要と指摘した以上、ロールバックも「追加したセクション / 関数 / CSS を削除する」だけ
- 結果: ロールバック節を簡素化する

### B-11. 状態遷移が暗黙のまま
- プランは「選択 → 比較表示 → 戻る」の画面遷移を書かない
- 批判: `app.js` は現在 `#listView` / `#detailView` の 2 状態 + `<dialog>` モーダル群。比較を「第 3 の section」にするなら、ナビ (`#listNav` / `#detailNav`) と FAB (`#floatingAddBtn`) の表示制御、`editMode` フラグとの相互作用、戻るボタン (`#backBtn`) の挙動を決める必要がある
- 結果: 状態遷移を先に決定する

### B-12. クラウド同期との相互作用が未検討
- 批判: 比較表示中に「元の旅を編集」すると、`Storage.save` → 700ms 後に `upsertCloudState` が走り、比較画面が古いデータを表示し続ける可能性
- 結果: 比較画面では**読み取り専用**を明示し、編集は元の旅程詳細に戻すかたちにする

## C. 改善後の設計案 (最小実装)

### C-1. スコープと非スコープ

**スコープ (今回やること)**
- 既存の 2 つの旅を「横並び」で比較表示する。比較対象は「日付の重なる 2 旅」を典型ケースとする
- 表示するのはサマリ (期間 / 項目数 / 予定合計 / 支払方法別 / 科目別) と「日別のタイムライン」を 2 列に並べたもの
- 比較は **読み取り専用**。編集は元の旅程詳細から行う

**スコープ外 (今回やらないこと)**
- 比較対象 3 つ以上
- 比較結果の保存 / 共有
- 比較結果の印刷 (`print/` は触らない)
- `state` の形変更 (version バンプ不要、`state.trips` も変更しない)
- 共通地点の自動抽出
- リファクタ (app.js 分割、`.bak` 整理、`.gitignore` 整備)
- 共同編集、変更履歴、自動差分保存

### C-2. 比較ロジックの意味を確定する

「2 旅を並べる」とは何かを 1 文で定義する:

> **同日が並ぶ**: 比較する 2 旅で開始日が同日 (または重なっている) とき、`day 1 / day 2 / ...` を左右で対応させ、左右の行を **同日の予定ペア** として縦に積む。片側にだけある項目は「片方のみ」と注釈して表示する。

開始日が 1 日以上ずれている場合は「左の旅の日付 + 右の旅の日付」を 2 行の列ヘッダとして出す。

### C-3. UI 構造

```
[比較モード] トグル (一覧の上部)
  OFF: 既存と同じ「開く / 複製 / 削除」の 3 ボタン
  ON:  カードにラジオボタン (2 つまで選択可) が出現、2 つ選んだ瞬間に「比較」ボタンが活性

[比較画面] <section id="compareView" hidden>
  ヘッダ: 「A: {tripA.name} ({tripA.startDate}〜)」「B: {tripB.name} ({tripB.startDate}〜)」
  サマリ: [項目数 / 予定合計 / 支払方法別 / 科目別] を左右 2 列
  タイムライン: 日 1 / 日 2 / ... を縦に積み、各日の中で左右 2 列
  戻るボタン: 一覧へ
```

ナビ (`#listNav` / `#detailNav`) は変更しない。比較画面はナビからではなく**一覧の上の「比較」ボタン経由**で開く。`#listNav` に戻れば元の状態。

### C-4. 状態

- 追加する永続状態: **なし**
- 追加する UI 状態 (揮発性): 
  - `compareMode: boolean` — 一覧のトグル
  - `compareSelection: string[]` — 選択中の tripId (最大 2)
  - `compareDay: number` — 比較画面内で表示中の日 (デフォルト 1)
- すべて `app.js` のモジュールスコープ変数で持つ。`Storage.save` は呼ばない

### C-5. 変更対象ファイル (確定)

| ファイル | 変更内容 | 触る箇所 |
|---|---|---|
| `index.html` | `<section id="compareView">` 追加、一覧のヘッダに「比較モード」トグル + 「比較」ボタン追加 | 4 行, 8 行目相当 |
| `js/app.js` | 比較モード切替、選択状態、比較画面描画 (`renderCompare()`)、`#compareView` ↔ 一覧の切替、戻る処理 | `list()` 拡張 + `renderCompare()` 新設 |
| `js/render.js` | `renderCompareSummary(tripA, tripB)` と `renderCompareDay(day, itemsA, itemsB)` を追加 | 末尾追記 |
| `js/utils.js` | `formatDayHeader(trip, day)` と `pairByDay(tripA, tripB)` を追加 | 末尾追記 |
| `styles.css` | `.compare-grid` (2 列) と `.compare-only-a` / `.compare-only-b` の注釈スタイル | 末尾追記 |

触らない: `model.js` / `storage.js` / `cloud.js` / `theme.js` / `editor.js` / `route-wizard.js` / `config.js` / `data/initial-state.json` / `styles.css` の差分コメント / `print/` 配下 / すべての `README*`

### C-6. データフロー

1. 一覧でトグル ON → `compareMode = true`、`list()` 再描画でラジオ表示
2. ラジオで 2 つ選択 → `compareSelection.length === 2` で「比較」ボタン活性化
3. 「比較」ボタン押下 → `#listView` を隠し `#compareView` を表示し `renderCompare()` を呼ぶ
4. `renderCompare()` は `state.trips` から `compareSelection` の 2 つを取り出し、`pairByDay` で日ごとに左右に分けて `renderCompareDay` に渡す
5. 戻るボタン押下 → `compareView` を隠し `#listView` を表示
6. 比較画面では編集不可。`#floatingAddBtn` は非表示、`#dayTabs` の代わりに「日 n」を単純に並べる

### C-7. マイグレーション / ロールバック

- マイグレーション: 不要 (`state` の形を変えない)
- ロールバック: 上記 5 ファイルの変更を逆マージするだけ。Supabase データも localStorage も触らない

### C-8. 失敗ケース

| ケース | 期待動作 |
|---|---|
| 旅が 0 件 | 比較ボタンは非活性 |
| 旅が 1 件 | 比較ボタンは非活性 |
| 2 件選択後、片方を削除 | 比較ボタンは非活性に戻る。比較画面は開かない |
| 比較中に 700ms 以内に元データを編集 | 比較画面は古いデータを表示し続ける (読み取り専用のため)。戻る → 再選択で最新を表示 |
| 比較中に同期エラー | 表示内容には影響なし (`#syncStatus` の表示変化のみ) |
| 開始日が大幅にずれている (例: 1 ヶ月違い) | 日の対応付けは開始日基準で単純に対応。完全に重ならない日は左右どちらかが空 |

### C-9. 検証チェックリスト

- 旅 0 件 / 1 件 / 2 件 / 3 件でトグル ON 時の挙動
- 2 件選択して比較 → サマリ値が左右でそれぞれ正しい (既存の `total` / `summarize` と一致)
- 1 件にだけ存在する day / item が「片方のみ」と表示される
- 編集モードで `#detailView` を開いて戻ってきても、比較画面の選択状態が壊れない
- ログアウト (`#logoutBtn`) しても比較選択は揮発性なので消える (期待動作)
- 印刷 (Ctrl+P) で比較画面が 1〜2 ページに収まる (`print/` 経由ではない、素のブラウザ印刷)
- 既存の `print/index.html?trip=ID` が壊れない (触っていないため)

### C-10. 実装タスク (順序)

1. `js/utils.js` に `formatDayHeader` / `pairByDay` を追加し、Node で算術テスト (可能な範囲で)
2. `js/render.js` に `renderCompareSummary` / `renderCompareDay` を追加
3. `index.html` に `<section id="compareView">` とトグル・比較ボタンを追加
4. `js/app.js` に比較モード状態、選択ロジック、`renderCompare()`、戻るハンドラを追加
5. `styles.css` に 2 列グリッドと注釈スタイルを追加
6. 手動で §C-9 のチェックリストを実行

### C-11. スコープ外として明示する事項 (再掲)

- 比較結果の保存 / 共有 / URL 化
- 比較結果の印刷ビュー (`print/` 未変更)
- 3 つ以上の同時比較
- 共通地点抽出
- `version` バンプ
- 既存のリファクタ
- 共同編集

## D. 修正済みプランの位置付け

このレビューは実装前の確認事項として残し、ユーザーが C 案で合意してから実装エージェントに渡す。
